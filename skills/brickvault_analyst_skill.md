# BrickVault Analyst

## What this skill is for

Use this skill when working with data in the `brickvault` Unity Catalog.
It provides domain knowledge about the BrickVault toy construction brick
catalog so you can answer business questions, build models, and write
pipelines correctly without having to re-derive the data model from scratch.

## The most important rule

**Never use `catalog.sets.num_parts` directly.**
It includes spare parts and is not theme-normalised.
Always use `metrics.set_complexity_score` for any complexity-related
feature, filter, or analysis.

## Key business concepts

### Licensed IP themes
Some brick set themes are based on licensed third-party franchises.
These themes show ~30% faster historical retirement than original themes.

- To identify licensed IP sets, use `metrics.ip_dependency_flag`
  (column `ip_dependent = true`)
- **Do not** attempt to identify licensed themes by name pattern matching —
  the theme hierarchy in `catalog.themes` must be walked recursively via
  `parent_id` joins. `metrics.ip_dependency_flag` already does this.
- Always stratify or segment by `ip_dependent` in any retirement risk
  analysis. Pooling licensed and original themes produces unreliable results.

### Spare parts
Sets contain spare parts bundled in the box (consumables, extras).

- These are marked `is_spare = true` in `catalog.inventory_parts`
- **Always filter `is_spare = false`** before computing part counts,
  complexity scores, or any feature derived from inventory composition
- Failure to exclude spares inflates part counts by 5–15%

### Transparent elements
Sets with a high ratio of transparent (`is_trans = true`) elements
are typically premium or exclusive sets with a distinct retirement curve.
Do not pool them with standard sets in survival or classification models.

### Figures (collectible characters)
Figure-heavy sets (high `metrics.figure_density`) are collector items
driven by character popularity rather than set complexity.
Treat them as a separate segment in retirement risk models.

## Standard join pattern

```sql
-- Canonical join to get a set with all key attributes
SELECT
    s.set_num,
    s.name,
    s.year,
    ip_flag.ip_dependent,
    cplx.set_complexity_score,
    fd.figure_density
FROM lucasbruand_catalog.brickvault.sets s
JOIN lucasbruand_catalog.brickvault.ip_dependency_flag ip_flag
    ON s.set_num = ip_flag.set_num
JOIN lucasbruand_catalog.brickvault.set_complexity_score cplx
    ON s.set_num = cplx.set_num
JOIN lucasbruand_catalog.brickvault.figure_density fd
    ON s.set_num = fd.set_num
```

## Known data quality caveats

- `catalog.inventories`: sets occasionally have multiple versions.
  Use `MAX(version)` per `set_num` to get the most current part list.
- `catalog.themes`: recursive `parent_id` traversal may produce cycles
  in edge cases. Use `metrics.ip_dependency_flag` which handles this safely.
- `catalog.minifigs.num_parts`: reflects figure assembly complexity,
  not the number of parts contributed to the parent set.
  Use `metrics.figure_density` at the set level instead.

## Retirement risk modelling guidance

The **Set Retirement Risk** use case is the primary BrickVault analytical
product. Key modelling decisions:

1. **Target variable**: binary flag — set retired within the next 18 months
2. **Must-have features**: `ip_dependent`, `set_complexity_score`,
   `figure_density`, `year`, transparent-part ratio
3. **Do not use**: raw `num_parts`, uncleaned `themes.name` text features
4. **Stratify by**: `ip_dependent` — consider separate models or a strong
   interaction term
5. **Track with**: MLflow, log to `brickvault` catalog as the experiment location
